# Система закупа и склада (интеграция с iiko) — воркфлоу v1

> Статус: черновик архитектуры процесса. Код не пишем — фиксируем логику, роли, статусы и закрываем пробелы.

---

## 0. Цель и принципы

**Цель:** снизить стоимость закупа, убрать ручную работу и сделать каждый сум прослеживаемым:
кто заказал → кто утвердил → что реально привезли → по какой цене → кто принял → кто заплатил → кто проверил.

**Три принципа, на которых держится вся схема:**

1. **Разделение обязанностей.** Заказывает, принимает, платит и проверяет — четыре разных человека. Один человек не проходит цепочку целиком.
2. **Ничего не удаляется, всё сторнируется.** Любое изменение после утверждения — новая версия + причина + автор + время.
3. **iiko — мастер по остаткам, мы — мастер по закупу.** Мы читаем номенклатуру/остатки/расход и записываем приходные накладные. Мы не правим остатки, не делаем инвентаризацию и списания — это остаётся в iiko.

## 2. Роли

| Роль | Что может | Чего НЕ может |
|---|---|---|
| **Инициатор** (шеф, бар-менеджер, су-шеф) | создать ручную заявку, править черновик | утверждать, принимать, платить |
| **Закупщик** | вести поставщиков и прайсы, выбирать поставщика, отправлять заказ | утверждать выше своего лимита, принимать товар, платить |
| **Утверждающий** (управляющий / директор) | утверждать заявки и отклонения сверх допуска | принимать товар, платить |
| **Кладовщик / принимающий** | приёмка по факту, фото накладной, брак / возврат | менять заказ, менять цену без основания, платить |
| **Бухгалтер** | заявка на оплату → платёж, привязка к накладной, сверка | менять заявку, приёмку и цены |
| **Контролёр / аудитор** | видит всё, комментирует, открывает спор | менять что-либо |
| **Админ** | справочники, лимиты, роли, интеграция | обходить журнал действий |

Правило: **утверждающий ≠ инициатор**, **принимающий ≠ закупщик**, **платящий ≠ принимающий**.
Если людей мало — система разрешает совмещение, но помечает такие операции флагом «совмещение ролей» в отчёте контролёра.

## БЛОК 1. Интеграция с iiko — синхронизация справочников

**Что тянем (только чтение):**

| Данные | Источник (iikoServer API, `/resto/api/...`) | Частота |
|---|---|---|
| Токен доступа | `auth` (login + sha1(pass)) → `logout` | по расписанию |
| Номенклатура (товары, ПФ, блюда, ед. изм., артикул) | `v2/entities/products/list` | 1 раз/час + по кнопке |
| Склады и подразделения | `corporation/stores`, `corporation/departments` | 1 раз/сутки |
| Поставщики (контрагенты) | `suppliers` | 1 раз/сутки |
| Прайсы поставщиков (если ведутся в iiko) | `suppliers/getPriceList` | 1 раз/сутки |
| Остатки на складах | `v2/reports/balance/stores` | каждые 15–60 мин |
| Расход / движение товара | OLAP `v2/reports/olap` (TRANSACTIONS) | 1 раз/сутки, ночью |
| Взаиморасчёты с контрагентами | `v2/reports/balance/counteragents` | 1 раз/сутки |
| Приходные накладные (обратная сверка) | `documents/export/incomingInvoice` | 1 раз/сутки |

> Точные пути и версии методов зависят от версии iikoServer — проверяем на боевом сервере на этапе интеграции. Логика блока от этого не меняется.

**Важно про лицензию:** токен iikoServer API привязан к лицензии и, как правило, допускает один активный сеанс. Поэтому **все обращения идут через один сервис-коннектор** с очередью запросов и обязательным `logout`. Никаких прямых вызовов из фронтенда или из нескольких сервисов сразу.

**Правила синхронизации:**
- Синхронизация инкрементальная, ключ — **GUID из iiko**. Наши внутренние id вторичны.
- Товар удалён / скрыт в iiko → у нас «архив»: из новых заявок исчезает, в истории остаётся.
- Новый товар в iiko → попадает в «Новые товары, не настроены» и **не участвует в авто-закупе**, пока не заданы нормативы и поставщик (Блок 3).
- Мы **не создаём** товары в iiko автоматически (см. пробел 16).

## БЛОК 2. Расход, остаток и товар «в пути»

Три числа, без которых авто-закуп считать нельзя:

1. **Остаток сейчас** — из iiko по конкретному складу (не по сети, а по складу).
2. **Средний расход в день** — по проводкам расхода за окно N дней (по умолчанию 28, настраивается 7 / 14 / 28 / 56).
   - Считаем по **фактическому списанию со склада** (проводки), а не по продажам блюд — так автоматически учитываются ТТК, полуфабрикаты и производство.
   - Из окна **исключаются аномалии**: банкеты, праздники, дни инвентаризации, акты списания порчи. Иначе один банкет раздувает норму на месяц.
   - Учитывается **день недели**: пятница-суббота у ресторана в 1.5–2 раза выше среды. Норма считается по профилю дней недели, а не плоским средним.
3. **В пути (open PO)** — сколько уже заказано и ещё не принято. Без этого числа система будет заказывать одно и то же дважды.

## БЛОК 3. Нормативы и расчёт потребности (авто-закуп)

**Карточка закупа товара** (наш справочник, привязан к товару iiko):

| Поле | Зачем |
|---|---|
| Склад | нормативы у кухни и бара разные |
| Мин. остаток (страховой запас) | ниже — сигнал тревоги |
| Период покрытия, дней | на сколько дней закупаем |
| Срок поставки (lead time), дней | наследуется от поставщика |
| Единица закупа + коэффициент к базовой | мешок = 25 кг, ящик = 12 шт |
| Кратность упаковки | нельзя заказать 1.3 мешка |
| Срок годности, дней | ограничивает период покрытия для скоропорта |
| Основной / альтернативный поставщик | Блок 6 |
| Сезонный коэффициент | опционально, на будущее |
| Статус: авто / только вручную / не закупаем | новые товары по умолчанию «только вручную» |

**Формула потребности:**

```
Потребность = СрРасходВДень × (LeadTime + ПериодПокрытия) + СтраховойЗапас
              − Остаток − ВПути

Заказ = вверх_до_кратности(Потребность / КоэффУпаковки) × КоэффУпаковки
```

Для скоропорта: `ПериодПокрытия = min(ПериодПокрытия, СрокГодности − LeadTime)`.

**Триггер авто-заявки:** остаток опустился ниже точки заказа (`СрРасходВДень × LeadTime + СтраховойЗапас`) **или** наступил день закупа по графику поставщика (напр. молочка — пн / чт).

Система формирует **черновик**, а не заказ. Рядом с каждой позицией видно, почему предложено именно это количество: расход, остаток, в пути, расчёт.

## БЛОК 4. Формирование заявки

- **4а. Авто-заявка** — по расписанию (напр. 06:00 ежедневно) и по графику поставщиков.
- **4б. Ручная заявка** — шеф / бар добавляет позиции, в т.ч. разовые (новое блюдо, банкет), с причиной и датой «нужно к».
- **4в. Заявка под событие / банкет** — отдельный тип: не влияет на расчёт средней нормы.

Черновик содержит: склад, позицию, кол-во авто, кол-во скорректированное, причину корректировки, предполагаемого поставщика, ожидаемую цену и сумму. Итог — сумма заявки и сравнение с бюджетом категории на месяц.

## БЛОК 5. Согласование

Матрица утверждения (настраивается):

| Условие | Кто утверждает |
|---|---|
| Сумма ≤ лимита закупщика | закупщик сам |
| Сумма > лимита закупщика | управляющий |
| Сумма > большого лимита, или новый поставщик | директор |
| Позиция вне номенклатуры / новый товар | управляющий + админ |

Утверждающий видит: сумму, отклонение от средней недельной, позиции, где количество увеличено вручную против расчёта, и позиции с ценой выше прошлой закупки.
Действия: утвердить / утвердить частично (по позициям) / вернуть с комментарием / отклонить. Всё пишется в аудит-лог.

## БЛОК 6. Разбивка по поставщикам и отправка заказа

1. Заявка разбивается на **заказы (PO)**: один PO = один поставщик + один склад + одна дата поставки.
2. Выбор поставщика: `основной` → если позиции нет или дороже порога → `альтернативный` → если ни у кого нет, позиция уходит в «нераспределённые» и требует решения человека.
3. Проверяются ограничения поставщика: **минимальная сумма заказа**, дни приёма заявок, дни доставки, время cut-off (заявка до 16:00 — привоз завтра). Не добрали до минимума — система подсказывает, чем добрать (позиции с ближайшей точкой заказа).
4. Отправка: PDF / Excel + сообщение. Каналы: Telegram, WhatsApp, e-mail, кабинет поставщика (на будущее). В заказе — номер, дата, склад, адрес, контакт принимающего, позиции **в единицах поставщика** и с **артикулами поставщика**.
5. Фиксируется: кто отправил, когда, каким каналом, кому. Отправка = момент, с которого товар считается «в пути».

## БЛОК 7. Ответ поставщика

Поставщик отвечает по каждой позиции: **подтверждаю / другая цена / другое количество / нет в наличии / замена**.
Способы: кнопка по ссылке без регистрации, либо закупщик вносит ответ вручную, либо интеграция — по возможностям конкретного поставщика.

Правила:
- Ответа нет до дедлайна (напр. за 2 часа до cut-off) → напоминание, затем эскалация закупщику.
- Отклонение цены **в пределах допуска** (по умолчанию ±3% и не более X сум) → авто-принятие с пометкой в отчёте.
- Отклонение **сверх допуска** → позиция уходит на переутверждение. Пока не утверждено — заказ не считается подтверждённым.
- «Нет в наличии» → система предлагает альтернативного поставщика или замену и формирует дозаказ.

## БЛОК 8. Приёмка

Работает **с телефона на складе**, с **офлайн-режимом**: данные сохраняются локально и досылаются при связи.

По каждой позиции принимающий вносит:
- **Факт количества** (заказано 10 → принято 10.5) — разница подсвечивается сразу.
- **Факт цены** из накладной поставщика.
- **Брак / некондиция**: сколько, причина, фото. Брак не приходуется, идёт в возврат.
- **Пересорт**: привезли не то — принять как другой товар (с привязкой к позиции iiko) или отказать.
- **Недовоз**: закрыть заказ или оставить открытым остаток на дозаказ.
- **Срок годности / партия** — для скоропорта, если включено.
- Обязательно: **фото или скан накладной поставщика**. Без него приёмку нельзя завершить — иначе контролёру нечего проверять.

Результат: документ приёмки с двумя колонками — «заказано» и «принято», по количеству и по цене, с итоговой суммой факта.

## БЛОК 9. Расхождения и эскалация

| Тип расхождения | В допуске | Сверх допуска |
|---|---|---|
| Количество (у весового товара свой допуск) | принимается автоматически | подтверждение утверждающего |
| Цена выше заказанной | принимается с пометкой | блокирует авто-приход, идёт на решение |
| Цена ниже заказанной | принимается, фиксируется как экономия | — |
| Недовоз | дозаказ или закрытие | решение утверждающего |
| Брак | возврат поставщику | уменьшение суммы к оплате или замена |

Любое расхождение сверх допуска создаёт **спор (dispute)**: статус, ответственный, срок, история переписки, итог (принято / возврат / скидка / замена).
Пока спор открыт — **оплата по этой накладной блокируется**.

## БЛОК 10. Авто-приход в iiko

Момент: **после завершения приёмки и закрытия всех блокирующих расхождений.**

- Создаётся приходная накладная (`documents/import/incomingInvoice`): склад, поставщик, дата, номер накладной поставщика, позиции **по факту** (количество, цена, сумма, НДС), в **базовых единицах iiko** — пересчёт из единиц поставщика делает наша система.
- **Идемпотентность:** храним ключ операции, повтор отправки не создаёт дубль. Сохраняем id документа iiko — это связь «наша приёмка ↔ накладная iiko».
- **Проводить или нет** — настройка. Рекомендация: проведённой, если расхождений нет; непроведённой + задача бухгалтеру, если расхождения были.
- **Ошибки** (товар не найден, склад не найден, iiko недоступен): приёмка не теряется, документ уходит в **очередь с ретраями**, ответственный получает уведомление. Статус приёмки — «принято, в iiko не выгружено».
- **Исправление:** ошиблись при приёмке — не правим молча. Создаётся корректировка: в iiko — исправление / сторно, у нас — новая версия с причиной и автором.
- **Обратная сверка:** раз в сутки выгружаем накладные из iiko и сверяем со своими. Если кто-то создал приход руками мимо системы — это видно в отчёте контролёра.

## БЛОК 11. Документы и рассылка

Формируются автоматически:
- **Акт приёмки** (заказано / принято / цена / сумма, роли-подписанты, фото накладной).
- **Протокол расхождений** — если были.
- **Реестр к оплате** по поставщику за период.

Рассылка по ролям (Telegram + e-mail, PDF): бухгалтеру — к оплате; утверждающему — сводка дня; контролёру — расхождения; директору — дневной / недельный дайджест (сумма закупа, топ отклонений, экономия).
Фиксируется факт доставки и прочтения; не прочитано в срок → повторное уведомление.

## БЛОК 12. Оплата, дебет–кредит, сверка

**Модель долга: учёт по документам, а не «вообще по поставщику».**

- У поставщика: условия оплаты (предоплата / по факту / отсрочка N дней), **кредитный лимит**, валюта.
- Каждая принятая накладная = **обязательство** со сроком платежа = дата приёмки + отсрочка.
- Бухгалтер работает через **заявку на оплату**: выбирает накладные, сумму (возможна частичная оплата и предоплата), способ (наличные / перечисление), прикладывает подтверждение платежа.
- Платёж **привязывается к конкретным накладным**, а не висит общей суммой — иначе сальдо никогда не сойдётся.

**Статусы по поставщику:**

| Показатель | Смысл |
|---|---|
| Кредит (мы должны) | сумма непогашенных накладных |
| Дебет (нам должны) | предоплаты, возвраты, недовозы, скидки по спорам |
| Сальдо | кредит − дебет |
| Просрочка | обязательства с наступившим сроком оплаты |
| Свободный лимит | кредитный лимит − текущий долг |

Свободный лимит исчерпан или есть просрочка → новый заказ этому поставщику требует утверждения директора (или блокируется — по настройке).

**Сверка:** периодически сопоставляем наше сальдо с `balance/counteragents` из iiko и с актом сверки поставщика; расхождения — в отчёт.

**Первичка (Узбекистан):** у поставщика — ИНН, договор, режим НДС; у накладной — номер ЭСФ / счёта-фактуры и ставка НДС. Без этого бухгалтерия период не закроет.

---

## БЛОК 13. Контроль и прозрачность

- **Аудит-лог на всё:** кто, что, когда, было → стало, причина. Неизменяемый.
- **Экран контролёра:** заказы с изменённой ценой; приёмки с расхождениями; приёмки без фото накладной; операции с совмещением ролей; накладные, созданные в iiko мимо системы; платежи без привязки к накладной.
- **Правило «четырёх глаз»** на суммах выше порога.
- **Полная цепочка по любой позиции** в один клик: расход → расчёт → заявка → утверждение → заказ → ответ поставщика → приёмка → накладная iiko → оплата, с документами и фото.

---

## БЛОК 14. Аналитика и оптимизация

- Динамика закупочной цены по каждому товару (график, % к прошлому месяцу).
- Сравнение цен поставщиков по одинаковым позициям + «сколько потеряли, купив не у дешёвого».
- **Рейтинг поставщика:** % недовозов, % брака, % отклонений цены от подтверждённой, соблюдение сроков.
- Оборачиваемость и «замороженные» деньги на складе; неликвид (лежит > N дней).
- План / факт бюджета закупа по категориям, foodcost.
- Экономия: подтверждённая (цена ниже прошлой), потенциальная (смена поставщика), потери (брак, списания, переплаты).

---

## БЛОК 15. Техническая надёжность

- Единый сервис-коннектор к iiko: очередь, ретраи с нарастающей задержкой, один активный токен, обязательный logout.
- Идемпотентность всех записей в iiko по ключу операции.
- Офлайн-режим приёмки с локальным хранением и синхронизацией.
- Справочники и остатки кешируются — приложение работает, даже если iiko временно недоступен (кроме создания прихода, который встаёт в очередь).
- Бэкапы, экспорт данных, журнал интеграционных ошибок с уведомлением админа.

## 16. Статусная модель заказа (сквозная)

```
DRAFT ──► PENDING_APPROVAL ──► APPROVED ──► SENT ──► CONFIRMED
                   │                                     │
                   ▼                          PARTIALLY_CONFIRMED
              REJECTED                                   │
                                                         ▼
                                                    IN_TRANSIT
                                                         │
                                                         ▼
                                                    RECEIVING
                                              ┌──────────┴──────────┐
                                              ▼                     ▼
                                          RECEIVED            DISCREPANCY
                                              │                     │
                                              │           ┌─────────┴────────┐
                                              │           ▼                  ▼
                                              │       RESOLVED          DISPUTED
                                              └───────────┤
                                                          ▼
                                                   POSTED_TO_IIKO
                                                          ▼
                                               AWAITING_PAYMENT ──► PARTIALLY_PAID
                                                          ▼              │
                                                        PAID ◄───────────┘
                                                          ▼
                                                       CLOSED
```

Отдельно: `CANCELLED` (до отправки), `RETURN` (возврат поставщику), `CORRECTION` (исправление проведённой приёмки).

## 18. Что нужно решить до старта разработки

1. **Сколько точек и складов**, нужна ли консолидация заказов по сети.
2. **Проводить ли приходную накладную в iiko автоматически** или создавать непроведённой под проверку бухгалтера.
3. **Где мастер по закупочным ценам** — в нашей системе (прайсы поставщиков) или в iiko.
4. **Каналы связи с поставщиками**: Telegram / WhatsApp / e-mail — что реально используют.
5. **Допуски**: на сколько % могут расходиться цена и количество без утверждения.
6. **Лимиты утверждения** по суммам и кто утверждающий.
7. **Работают ли в долг**, у кого какая отсрочка — от этого зависит объём блока 12.
8. **Версия iikoServer и доступ к API** (учётка с нужными правами) — от неё зависят точные методы.
